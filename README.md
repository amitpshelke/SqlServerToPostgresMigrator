# SQL Server → PostgreSQL Migration Tool

## Development Progress & Phase-wise Implementation Notes

## Project Overview

The tool is being developed in **.NET/C#** to migrate an existing SQL Server-backed microservices database to PostgreSQL.

The solution separates:

- Metadata discovery
- Schema generation
- Data migration
- Validation
- Reporting
- Logging
- Planned migration-state/resume functionality

## Solution Structure

| Project | Responsibility |
|---|---|
| `MigrationTool.Cli` | Command-line interface and migration commands |
| `MigrationTool.Core` | Models, interfaces, migration orchestration, validation, reporting and services |
| `MigrationTool.SqlServer` | SQL Server metadata and data access |
| `MigrationTool.PostgreSql` | PostgreSQL schema/data writing and identity synchronization |
| `MigrationTool.Mapping` | SQL Server → PostgreSQL type/value mapping |
| `MigrationTool.Reporting` | Reporting-related functionality |
| `Tests` | Unit/integration-oriented test projects |

# Phase 2 — Complete Schema Migration

**Status: COMPLETE**

Expanded schema migration from tables/columns to the major relational objects required by the application.

### Implemented

- Primary keys, foreign keys, unique constraints and check constraints.
- Default constraints and indexes.
- Identity column handling.
- `PostgreSqlSchemaWriter` and constraint/index generation.
- Idempotency checks so existing PostgreSQL constraints/indexes are not recreated.

### Important Fixes

- SQL Server `timestamp`/`rowversion` compatibility data mapped to `BYTEA`.
- Identity syntax corrected to PostgreSQL-compatible `GENERATED BY DEFAULT AS IDENTITY`.
- SQL Server defaults mapped to PostgreSQL equivalents such as `CURRENT_TIMESTAMP` and `gen_random_uuid()`.
- Boolean defaults converted to PostgreSQL `true`/`false` values.
- PostgreSQL identifiers use quoting such as `"dbo"."tbl_Role"`.

# Phase 3 — Data Migration Engine

**Status: COMPLETE**

Implemented the actual SQL Server → PostgreSQL row migration pipeline with streaming and progress reporting.

### Implemented

- `SqlServerDataReader` for streaming SQL Server rows.
- `PostgreSqlDataWriter` using PostgreSQL binary `COPY`.
- Streaming migration to avoid loading complete tables into memory.
- SQL Server value conversion to PostgreSQL-compatible values.
- Identity sequence synchronization after data migration.
- `IProgress<MigrationProgress>` support.
- Per-table error handling.
- `migrate-data --table`.
- `migrate-data --all`.
- Foreign-key dependency ordering.

### Important Behavior

Progress represents **rows read/streamed from SQL Server**, while `RowsMigrated` in the final result represents **successfully completed target migration**.

Therefore, a `COPY` failure can show:

```text
32/32
```

progress while the final:

```text
RowsMigrated = 0
```

This distinction is intentional and helps separate source-read progress from successful target completion.

# Phase 5 — Reporting, Logging & Migration State

**Status: IN PROGRESS**

## 5.1 — MigrationTableResult

**Status: COMPLETE**

Introduced a structured result for each table migration.

### Features

- Tracks table name, status, rows migrated, total rows, timestamps and duration.
- Supports the following states:
  - `Pending`
  - `Running`
  - `Success`
  - `Failed`
  - `Cancelled`
- Stores `ErrorCode` and `ErrorMessage` for failures.

---

## 5.2 — MigrationReport

**Status: COMPLETE**

Aggregates table-level results into a migration-level report.

### Features

- Tracks planned, attempted, successful, failed, cancelled and not-started tables.
- Calculates total migrated rows and duration.
- Determines overall success.
- Provides filtered successful, failed and cancelled result collections.

---

## 5.3 — DataMigrationService Integration

**Status: COMPLETE**

Connected the structured result/report models to the migration engine.

### Implemented

- `MigrateTableAsync` returns `MigrationTableResult`.
- `MigrateAllTablesAsync` returns `MigrationReport`.
- Failures and cancellation become structured results.
- Full migration stops at the first failure to preserve dependency-safe behavior.

---

## 5.4 — MigrationLogger

**Status: COMPLETE**

Added structured migration logging using `Microsoft.Extensions.Logging`.

### Implemented

- `IMigrationLogger` and `MigrationLogger`.
- Logs migration start/completion/cancellation.
- Logs table start/completion/failure.
- Registered through dependency injection.

---

## 5.4.1 — Migration Error Formatting

**Status: COMPLETE**

Converts verbose PostgreSQL exceptions into concise migration errors.

### Implemented

- Captures PostgreSQL SQLSTATE codes.
- Uses safe metadata such as constraint, table and column names where available.
- Handles common PostgreSQL errors including:
  - `23505`
  - `23503`
  - `23502`
  - `23514`
  - `42P01`
  - `42703`
  - `42601`
  - `22001`
  - `22P02`
- Keeps `ErrorCode` separate from `ErrorMessage`.

---

## 5.5 — Detailed Migration Report

**Status: COMPLETE**

Added `MigrationReportFormatter` for readable CLI reporting.

### Features

- Shows timestamps, duration and migration summary.
- Shows table-by-table status, row counts and duration.
- Shows error code and formatted error message for failures.
- Separates **Total Rows** from **Rows Migrated**.

---

## 5.6 — Failed-table Tracking

**Status: COMPLETE**

Added convenient access to failed, successful and cancelled table results.

### Benefits

- Supports future retry/resume decisions.
- Makes failed-table identification explicit rather than requiring report filtering by callers.

---

## 5.7 — Resume Capability

**Status: COMPLETE**

Planned persistent migration state and resume support.

### Planned / Implemented Capabilities

- Persist migration execution state as JSON.
- Assign a migration ID.
- Persist each table's status/result.
- Skip successful tables on resume.
- Retry failed/cancelled tables and continue with not-started tables.
- Add a CLI option such as:

```bash
migrate-data --resume <migration-id>
```

- Schema validation command:

```bash
validate --schema
```
